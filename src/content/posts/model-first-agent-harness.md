最近在开发自己的文献研究 Agent 时，我逐渐形成了一个认识：

**随着基础模型能力不断增强，Agent Harness 的设计重心应该从弥补模型的认知缺陷，转向放大模型的原生能力。**

过去，我们为了应对模型的幻觉、有限的推理能力和不稳定的任务规划，设计了大量复杂的工作流，包括任务拆解、多 Agent 协作、结构化中间结果、强制反思、多轮审核等。

这些设计在特定阶段是合理的。但当模型本身已经具备较强的规划、推理、工具使用和自我纠错能力时，曾经用于弥补能力不足的 Harness，也可能反过来成为限制模型能力的瓶颈。

这个认识并非来自纯粹的架构推演，而是来自最近六轮并不算成功的工程实验。

## 一、一次逐渐走向复杂的 Agent 开发

我正在开发一个名为西娅的科研辅助 Agent，希望它能够自主完成跨学科文献检索、论文阅读、研究分析和报告生成。

最初的设计其实非常简单：

**多路召回 → 粗筛 → 精筛 → 原文阅读 → 校对 → 交付。**

为了增强论文发现能力，我陆续引入 OpenAlex、DBLP 等专业学术检索工具，并保留通用网页搜索和 Crossref 书目核验。

这些改动取得了明确的收益。专业学术数据库能够发现通用搜索遗漏的论文，而网页搜索又能够补充数据库尚未收录的最新研究和正式出版信息。

但随着研究任务逐渐复杂，一些问题开始暴露出来：

- 找到了正确的论文，却总结错了实验结果。
- 论文中的数字都是真实的，但统计分母和比较对象被混淆。
- 已经发现的重要论文没有进入最终报告。
- 搜索和阅读都已完成，却因为最后一次模型调用失败而丢失全部成果。

为了逐个解决这些问题，我开始不断增强 Harness。

先建立统一论文候选池，再增加批量精筛、全局论文取舍、结构化事实提取、原文证据绑定、独立语义核验、最终逐段校对和多轮修订。

每增加一层机制，似乎都能找到充分的理由。但当这些机制组合起来之后，整个研究系统开始变得异常复杂。

在一次真实的跨学科文献研究中，系统发现了113篇候选论文，对23篇论文进入阅读处理，提取了645条研究事实，其中629条被内部核验器标记为支持。

整个过程执行了189个研究阶段。

然而，最终并没有完成完整的研究综述，用户实际只收到了1000字的部分结果。

其中存在独立的交付缺陷，但也暴露出了一个更值得思考的问题：我们投入了大量资源组织和核验研究材料，却没有证明这些额外机制能够带来更好的研究结果。

**Harness 越来越复杂，Agent 却没有因此变得更可靠。**

## 二、一次出乎预期的对照实验

在第六轮实验中，我决定重新建立一个最简单的基线。

不再强制模型进行细粒度事实提取，也不要求每条研究结论都经历独立核验，而是直接将筛选后的论文原文交给强模型，让它自主阅读、理解和综合分析。

实验固定了四篇软件测试论文的可用原文，并预先封存18项研究质量评价标准。

结果如下：

| 方案               | 模型请求次数 | 输入 Token | 完整覆盖标准 |
| ------------------ | -----------: | ---------: | -----------: |
| 强模型直接阅读     |            1 |     31,047 |        18/18 |
| 研究卡片与多轮核验 |           16 |    304,132 |        16/18 |
| PaperQA 检索与补读 |           22 |     25,405 |         8/18 |

在另一组包含三篇血压随机试验论文的实验中，直接阅读方案完整覆盖16项标准、部分覆盖2项，同样优于其他候选方案。

这些实验规模有限，PaperQA 使用的也是较简单的稀疏检索配置，因此不能据此否定复杂工作流或学术 RAG 在其他场景中的价值。

但至少在原文能够容纳于模型上下文的情况下，结果非常值得反思。

复杂核验方案消耗了近十倍的输入 Token，却没有获得更好的研究质量。

更有意思的是，部分正确的研究结论恰恰是在核验阶段被改错的。

模型第一次阅读完整论文时，能够正确理解实验对象、样本数量、统计范围和比较关系。但后续核验器只接收经过裁剪的证据窗口，缺少完整上下文，于是将原本正确的结论标记为证据不足，甚至直接删除。

我们原本试图通过 Harness 减少模型犯错的概率，却在不同阶段的信息转换过程中引入了新的错误。

这让我意识到：

**额外的模型调用并不天然意味着额外的智能，更多的计算也不天然意味着更好的推理。**

如果这些计算主要用于重复拆解、转换和审核已经正确的信息，那么它们可能产生的是负收益。

## 三、我们可能低估了强模型的能力

回顾整个开发过程，我发现自己一直在沿用一种面向弱模型的工程思维。

担心模型无法正确规划，于是预先设计研究流程。

担心模型遗漏论文，于是增加多阶段取舍和覆盖检查。

担心模型理解错误，于是要求先提取结构化事实。

担心结构化事实不准确，于是增加独立语义核验。

担心最终报告表达错误，于是再次进行逐段校对。

这些设计背后其实有一个共同的假设：

**开发者预先规定的任务执行方式，比模型自主选择的方式更加可靠。**

对于能力有限的模型，这个假设可能成立。

但随着模型具备更强的长上下文理解、复杂推理和自主规划能力，这个假设就需要重新验证。

一个强模型可能已经能够在一次推理过程中同时理解多篇论文、区分实验条件、发现数据冲突并完成跨论文比较。

此时，强制将其拆分为多个相互独立的阶段，不仅会增加执行开销，还可能破坏原本完整的推理上下文。

这就像聘请了一位能力很强的研究人员，却不允许他直接阅读论文，而是要求他依据其他环节整理出来的材料，按照几十道审批流程完成研究。

流程看起来更加严谨，但研究人员能够接触的信息和自主判断的空间反而变少了。

## 四、Harness 的价值正在发生转移

我并不认为随着模型变强，Harness 会变得不再重要。

恰恰相反，强模型可能比弱模型更需要高质量的 Harness。

只是 Harness 的建设方向应该发生变化。

| 维度     | 面向弱模型的设计   | 面向强模型的设计     |
| -------- | ------------------ | -------------------- |
| 任务规划 | 预定义工作流       | 提供自主规划空间     |
| 工具调用 | 固定执行顺序       | 提供高质量工具与反馈 |
| 推理过程 | 强制任务拆解       | 保留完整推理上下文   |
| 上下文   | 预先提取和加工信息 | 按需加载、可恢复压缩 |
| 质量保障 | 多轮强制审核       | 自主纠错与必要验证   |
| 失败处理 | 重新执行任务       | 状态保存与局部恢复   |

过去的 Harness 更像一个控制系统，试图确保模型按照开发者设计的方式完成任务。

未来的 Harness 应该更像一个能力放大器，为模型提供足够丰富、可靠的执行环境，让模型自主决定如何解决问题。

相比继续设计复杂的认知工作流，我认为以下几个方向具有更长期的工程价值。

### 1. 更好的工具

模型的能力不仅取决于其内部知识和推理水平，还取决于它能够访问什么、观察什么，以及执行什么。

对科研 Agent 而言，专业学术数据库、引文网络、原文获取、论文检索和文档阅读工具，可以直接扩大模型的研究能力边界。

对 Coding Agent 而言，源码检索、运行日志、测试环境、性能分析和调试工具同样重要。

与其硬编码一套排查问题的流程，不如让模型能够接触更完整的源码、日志和运行时证据。

模型越强，高质量工具所能带来的增量可能就越大。

### 2. 更好的上下文管理

上下文工程不应该只是尽可能减少 Token，而应该研究如何让模型在有限的上下文容量中获得充分且可靠的信息。

对于能够直接容纳的原始材料，没有必要提前进行有损压缩。

对于超出上下文容量的材料，可以通过分层索引、按需读取、上下文压缩和原文回溯等机制，使模型能够在需要时恢复完整信息。

尤其重要的是，压缩后的内容应该保留与原始证据之间的关联。

**好的上下文压缩应该是可恢复的，而不是不可逆的信息丢弃。**

模型不一定需要始终看到全部信息，但它应该具备在需要时重新获取信息的能力。

### 3. 更好的状态管理与失败恢复

无论模型多么强大，它都无法仅凭推理能力保证网络请求一定成功、进程不会崩溃、模型服务不会超时、文件一定能够上传。

这些是确定性的工程问题，也是 Harness 最应该负责的事情。

包括状态持久化、Checkpoint、局部重试、幂等控制、任务隔离、模型降级以及异常情况下的部分成果交付。

在西娅的实验中，可靠交付机制就是一项具有明确价值的改进。

即使最终综合模型失败，已经取得的研究成果也不应该丢失。系统应该保存原始材料、论文记录及已有分析，并尽可能将它们交付给用户。

这种能力不会因为未来模型变得更强而失去价值。

### 4. 更充分的资源与探索空间

强模型往往能够根据任务复杂度自主决定需要进行多深的调查、多少次工具调用，以及是否需要进一步核验。

Harness 应该提供充分但有界的计算资源，而不是过早规定所有任务只能执行相同数量的步骤。

简单任务可以快速完成，复杂任务可以深入探索。

在资源允许的情况下，应优先让额外计算用于发现新的证据、解决尚未解决的问题，而不是机械地重复已经完成的推理过程。

## 五、轻量化不意味着取消约束

这里需要特别区分两种复杂度：

**认知控制的复杂度，以及工程保障的复杂度。**

前者应该随着模型能力提升而重新评估，后者仍然需要持续建设。

例如，在数据库写入、生产部署、权限控制和资金交易等场景下，即使模型拥有极强的推理能力，程序仍然需要提供严格的权限校验、事务约束、审批机制和操作边界。

这些约束并不是为了弥补模型不够聪明，而是为了保证系统必须遵守的正确性条件。

同样，在科研任务中，论文身份、引用真实性、明确的发表资格等要求，也应该保留可验证的证据和必要的确定性检查。

因此，我更倾向于这样划分职责：

- 确定性问题交给程序。
- 开放性的认知问题交给模型。
- 不可逆操作设置严格的执行边界。
- 可逆的探索性任务给予模型充分自由。
- 针对经过实验确认的能力缺口，引入必要的约束。

Harness 的轻量化不是减少工程投入，而是将工程投入放在更有价值的位置。

**轻认知控制，重执行基础设施。**

## 六、设计能够受益于模型升级的 Harness

我认为判断一个 Harness 机制是否值得长期投入，可以提出一个问题：

**如果明天基础模型的能力大幅提升，这个机制是否仍然有价值？**

如果一个机制主要用于弥补当前模型的规划和推理缺陷，那么随着模型升级，它的收益可能逐渐减小，甚至成为负担。

但高质量工具、原始数据访问、上下文管理、状态持久化、运行时反馈和失败恢复，不仅不会因为模型升级而失去价值，反而可能被更强的模型利用得更加充分。

这也是我希望未来 Agent 系统能够具备的一个特征：

不是每次模型升级都需要重新设计工作流，而是能够通过替换更强的基础模型，自然获得更好的任务完成能力。

在研发过程中，也应该先建立充分发挥模型原生能力的简单基线，再通过对照实验逐步增加 Harness 机制。

如果额外机制无法改善任务质量，就不应该仅仅因为它在架构上看起来更加严谨而保留。

## 写在最后

经过这几轮实验，我逐渐从 Workflow-first 的思路转向 Model-first、Harness-assisted。

过去，我更关心如何设计一套足够完善的工作流，让模型按照正确的方式完成任务。

现在，我更关心如何为模型提供足够好的工具、足够完整的上下文、足够充分的探索空间，以及足够可靠的执行环境。

至于具体如何规划、如何推理、如何解决问题，在模型能力允许的范围内，应该更多地交给模型自己决定。

这并不是说强模型不会犯错，也不是说复杂工作流没有价值，而是我们不应该在没有验证必要性的情况下，提前用工程机制限制模型的能力。

**随着模型越来越强，Harness 最重要的职责或许不再是教模型如何思考，而是让模型能够充分思考，并保证思考的成果能够可靠地转化为现实结果。**

一个好的 Harness，应该成为模型能力的放大器，而不是模型能力的上限。
